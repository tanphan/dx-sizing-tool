What changed on 17 Nov 2026. Results differ from earlier versions:
  • Load multiplier and growth are applied once. Earlier versions applied them twice, so a 2× load showed 4× RPS.
  • Think time above 0 now sets the request rate. The default is 0, which keeps the session-based rate.
  • DAM assets go HAProxy → DAM, are counted inside requests per session, and have their own cache hit ratio.
  • Core / webEngine pods are fixed at the HCL size (5.6 CPU, 8Gi). The tool adds replicas for CPU or session heap instead of growing pods.
  • The Helm export uses the chart's real key paths, with requests equal to limits.

2. What this tool does

Given business/usage inputs (peak users, session length, search/DAM attach rates, etc.), the tool produces two views from the same sizing engine:

Estimator

BOM table: replicas, CPU, memory, storage, util, infra cost, license cost, AI tokens. Session panel + CSV/JSON/Helm export.

Simulator

Topology graph with RPS on edges, util coloring, load slider (0.1×–5×), scenario presets, and fix actions (add replica / enable CDN).

Switching product DXCN ↔ DX Compose swaps the component catalog (Core vs webEngine; Remote Search only on DXCN) but keeps one math kernel so estimator and simulator never disagree.

Auth topology. External IdP (OIDC/SAML) is not reached via HAProxy. The browser redirects to the IdP; Core / webEngine call the IdP back-channel (token, JWKS, etc.). OpenLDAP binds are also Core/webEngine → LDAP directly. ACS/callback traffic returns as normal portal RPS through HAProxy.
DAM routing. Browsers fetch assets (/dx/api/dam/…) through HAProxy straight to DAM. They do not pass through Core / webEngine. HAProxy and the origin WAF / load balancer carry both page and DAM traffic.
Cloud & production. The sidebar picks a cloud provider (AWS EKS, Azure AKS, Google GKE, Red Hat OpenShift), which adjusts unit costs and labels platform SKUs. Production platform adds the origin WAF, cloud load balancer, DB secondary, secrets/KMS, observability, backup/DR, registry and egress NAT. Traffic then flows CDN miss → WAF → cloud LB → HAProxy.

6.2 Advanced

Searches/hit, peak authoring users, uploads/day & avg MB, content items (index GB), IQ attach / msgs / tokens in+out, growth CAGR, session footprint KB.

Think time (sec). When above 0, the request rate is U_peak ÷ think time. This is how a Locust virtual user behaves (wait_time); for between(1, 3) use 2. Use it when your users figure comes from a load test. Leave it at 0 for real visitors, who are paced by requests per session. The Estimator warns when the two methods differ by more than 2×.

7. Estimator

Summary cards show front-door RPS, portal RPS, concurrent sessions, infra $, license $, AI tokens $, total $, and profile confidence.

  • Session math — concurrent sessions, sessions/day, footprint Mi, recommended timeout, sticky-session note for HAProxy.
  • BOM table — per component: replicas, offered/capacity RPS, util, CPU, mem, storage, infra $, license $.
  • Util colors — green <70% · amber 70–90% · red >90%.
  • Warnings — default-profile confidence, CDN miss=0, bottlenecks, Compose Remote Search ignored, think time vs session pacing mismatch, etc.
Core / webEngine pods. Each pod is sized at the HCL K8s guide shape: 5.6 CPU, 8Gi memory (request = limit), 4Gi heap with Xms = Xmx. Replicas are the largest of four numbers:
  • RPS ÷ rpsPerReplica
  • The HA / AZ floor
  • The pods needed for CPU (idle CPU + cpuPerRps × RPS must fit within 5.6 per pod)
  • The pods needed for session heap (session memory must fit within 50% of the 4Gi heap per pod)
The node notes show estimated CPU and heap used per pod. The 50% heap share and the 30% session-memory safety factor are tool assumptions, not HCL figures.

8. Simulator

  1. Open the Simulator tab. Graph auto-layouts from the active product topology.
  2. Edge labels show traffic class + RPS; edges animate when RPS > 0.
  3. Use the Load slider (0.1×–5×) to stress the design. At ~3× peak you should see amber/red on hot path nodes.
  4. Click a node for util, replicas, cost, and notes.
  5. Add replica raises that node’s replica override and recomputes util/cost.
  6. Enable CDN restores cache-hit path (uncheck CDN to force miss-through).
  7. Reset fixes clears overrides and sets load back to 1×.
Simulator and Estimator call the same runSizing() function. Node panel numbers match the BOM for identical inputs (except temporary replica overrides / CDN toggle in the sim).

9. Calibrate (Locust → profile)

Default profiles are conservative placeholders. To make numbers trustworthy on your lab:

  1. Run Locust scenarios; measure steady-state RPS and CPU per component (and replica count).
  2. Open Calibrate. Paste JSON like:
{
  "measurements": [
    { "componentId": "core", "rps": 140, "cpuCores": 6, "replicas": 2, "util": 0.7 },
    { "componentId": "haproxy", "rps": 800, "cpuCores": 0.4, "replicas": 2, "util": 0.5 }
  ]
}
  1. Click Apply calibration. A lab profile is registered (e.g. dxcn-cf238-lab) with confidence: lab-calibrated.
  2. Optionally Export Locust scenario mix (browse/author/form/search/DAM/IQ weights) for AIOps alignment.
  3. Sample file: scripts/sample-locust-measurements.json.

Patch formula (approx): rpsPerReplica ≈ observed_rps / replicas / util; cpuPerRps ≈ (cpuCores / replicas − cpuBase) / (rps / replicas). cpuBase is the profile's idle CPU (2 for Core), not the 5.6 CPU pod size. With the sample above, Core gets rpsPerReplica 100 and cpuPerRps ≈ 0.0143. Memory is not calibrated.

10. Live vs estimate

  1. Capture kubectl top pods (or paste an AIOps-style summary in the same columns).
  2. Open Live vs est, paste, click Compare vs estimate.
  3. Pod names are matched by substring map (dx-core→core, haproxy, web-engine, dam, …).
  4. Status: ok · over (live ≫ estimate) · under (live ≪ estimate) · missing (no match).

12. How the math works (short)

scale        = loadMultiplier × (1 + CAGR)              (applied once)
U_peak       = peakConcurrentUsers × scale
pacing       = thinkTime            if thinkTime > 0
             = T_session_min × 60 / req_per_session     otherwise
frontDoorRps = peakRpsOverride × scale                  if override > 0
             = U_peak / pacing                          otherwise

damShare     = damRequestShare  OR  a·n / (1 + a·n)     (a = damAttach, n = assetsPerPage; 0 if DAM off)
damRps       = frontDoorRps × damShare × (1 − damCacheHitRatio)      HAProxy → DAM
portalRps    = frontDoorRps × (1 − damShare) × (1 − cacheHitRatio)  HAProxy → Core/webEngine
originRps    = portalRps + damRps                       (WAF / LB / HAProxy; HAProxy also carries IQ)

searchRps    = portalRps × searchAttach × searchesPerHit   (if search enabled)
imageRps     = 0.2 × damRps
iqRps        = U_peak × iqAttach × msgs / sessionSec       (own traffic class)

replicas     = max( ceil(offeredRps / rpsPerReplica), haMin, azCount, minReplicas )
util         = offeredRps / (replicas × rpsPerReplica)

Core/webEngine (pod fixed at 5.6 CPU / 8Gi, heap 4Gi):
  cpuReplicas  = ceil( cpuPerRps × RPS / (5.6 − cpuBase) )
  sessionHeap  = U_peak × sessionBytes × 1.3
  heapReplicas = ceil( sessionHeap / (4Gi × 0.5) )
  replicas     = max( replicas, cpuReplicas, heapReplicas )

tokens/mo    = sessions/day × 30 × iqAttach × msgs × (tok_in + tok_out)
DAM storage  ≈ uploads/day × avgMB × 30 × retention / 1024  Gi

Edge labels in the Simulator show the same absolute RPS as the node they point to.

Capacity constants live in src/profiles/dxcn-cf238.json and src/profiles/compose-cf237.json (rpsPerReplica, cpuPerRps, memBaseGi, HA floors, etc.).

13. Worked example

Scenario: 5,000 peak concurrent users · 40% search attach · 10% DAM · IQ off · DXCN · cache hit 0.4

  1. Select DXCN. Leave defaults (or set peak users = 5000, search attach = 0.4, DAM attach = 0.1).
  2. Enable Remote Search and DAM (DAM auto-enables Ring + image + persistence).
  3. The Estimator shows Core at ≥ 2 replicas of 5.6 CPU / 8Gi each (HA floor). DAM is sized from its share of requests after the DAM cache, and Remote Search from fan-out RPS. Infra and license totals are shown separately.
  4. In the Simulator, DAM hangs off HAProxy (assets /dx/api/dam), not off Core.
  5. Open Simulator → slide load to 3×. Expect Core (and possibly search/DAM) to move amber/red.
  6. Click the red node → Add replica until util drops under 70%, or raise cache hit / lower attach rates.

14. Troubleshooting

SymptomFix
npm can’t find package.jsonRun from dx-sizing-tool/, not the repo root
Remote Search on ComposeExpected — Compose forces it off; use Search V2
Always 2+ Core/webEngine replicasHA/AZ floor by design (never recommend 1 for prod)
Huge portal RPSCheck think time: a value above 0 models load-test users, which send far more requests than real visitors. Otherwise raise the page cache hit ratio or set a peak RPS override.
Lower RPS than an older versionExpected. Earlier versions applied load multiplier and growth twice.
Core / webEngine always exactly 5.6 CPU / 8Gi per podBy design (HCL pod shape). Load shows up as more replicas; see the node notes for which limit drove the count.
Saved inputs lack the new DAM fieldsThe DAM cache hit ratio falls back to the page ratio and request share to 0. Set them in the sidebar, or clear saved state.
Live compare all “missing”Pod names don’t match map — rename needles or include core/haproxy/dam substrings
Stale UI stateClear localStorage key dx-sizing-tool-v1
